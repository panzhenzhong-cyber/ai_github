从零搭建 Go CLI 的 CI/CD 发布链路

一个几十行的程序也值得拥有可靠的交付方式。本文用 AI GitHub 项目说明，怎样把本地代码稳妥地送到可下载的跨平台二进制。

GoGitHub Actions约 8 分钟

这个项目的功能很简单：接收名字并输出问候，或者打印版本号。真正值得记录的不是功能本身，而是围绕它建立的一套完整工程闭环。

目标不是“让 CI 亮绿灯”，而是让每次改变都经过同一套可重复的验证，并能产出用户真正可以运行的文件。

01. 先把程序边界变得可测试

命令行程序经常把参数解析、业务逻辑和输出全部塞进 main。这样能跑，却很难测试。项目把可验证逻辑放进独立包，让入口只负责连接参数与输出。

func Greeting(name string) string {
    if strings.TrimSpace(name) == "" {
        name = "World"
    }
    return fmt.Sprintf("Hello, %s!", name)
}

测试覆盖默认值和自定义名字。CI 不需要启动外部服务，就能快速判断核心行为有没有被破坏。

02. 用一个命令统一本地与远程检查

开发者在本地运行的检查，应该和 GitHub Actions 中执行的检查一致。项目用 make check 汇总格式、静态分析、测试和构建：

check: fmt-check vet test build

fmt-check:
    test -z "$$(gofmt -l .)"
vet:
    go vet ./...
test:
    go test -race ./...
build:
    go build ./cmd/ai-github

这减少了“本地可以、CI 不行”的差异，也让任何协作者——包括 Codex——都能在提交前执行相同的质量门槛。

03. CI 负责证明每个提交仍然健康

推送或 Pull Request 会触发工作流。它检出代码、安装指定 Go 版本，然后运行统一检查。依赖缓存交给 Go 工具链和 Actions 处理，配置保持短小透明。

这里最重要的设计是：CI 只验证源码，不悄悄修改仓库。格式错误直接失败，开发者在本地修正后重新提交，历史因此更清晰。

04. 标签触发真正的跨平台发布

当版本准备好后，推送形如 v0.1.0 的标签。发布工作流分别构建 Linux、macOS、Windows 的 amd64/arm64 文件，并为产物生成 SHA-256 校验值，最后附加到 GitHub Release。

GOOS=linux   GOARCH=amd64 go build ...
GOOS=darwin  GOARCH=arm64 go build ...
GOOS=windows GOARCH=amd64 go build ...

用户不需要安装 Go，也不需要信任某台开发电脑上的手工构建，只需下载对应平台文件并核对校验值。

05. 把网站也放进同一条交付链路

web/ 是纯 HTML、CSS 和 JavaScript，不依赖构建框架。只要该目录发生变化，Pages 工作流就上传静态文件并部署到 GitHub Pages。这个博客本身就是这条链路的产物。

06. 让自动化提交保留清晰身份

由 Codex 完成的提交使用单次 Git 身份参数，而不修改用户的全局配置：

git -c user.name=Codex \
    -c user.email=codex-bot@localhost \
    commit -m "feat: ..."

这样 git log 能明确显示提交者，同时用户自己的名字和邮箱保持不变。身份清晰，是人机协作流程中很小但很重要的一环。

结语

小项目是搭建工程能力的好地方：反馈快，问题边界清楚。最终我们得到的不只是一个 Go 二进制，而是一条从修改、验证、审查到发布和展示都可重复的路径。
